## 三、分析工作的核心原则

### 原则一：技术栈完全开放，先发现再分析

不要以已知的 Java、Python、前端代码为边界。

先完整识别当前仓库内实际存在的技术组件。

应根据实际代码和配置识别：

- 编程语言及各自承担的职责
- 前端框架及页面组织方式
- 后端框架及服务划分
- 独立服务、公共模块和共享库
- 数据处理程序、命令行工具和脚本
- 定时任务、后台 Worker 和任务调度系统
- 工作流引擎或流程编排组件
- 数据库、ORM、SQL 脚本及存储过程
- 缓存、消息队列、事件总线和 RPC
- API Gateway、代理、认证及鉴权组件
- 外部系统、第三方 SDK 及集成接口
- 容器化、CI/CD、基础设施和部署配置
- 测试框架、日志、监控和链路追踪
- 其他影响业务运行的重要技术

这些是需要检查的技术类别，不代表项目一定使用了它们。

必须根据实际证据判断是否存在。

请特别区分：

- 仓库中存在某项技术
- 该技术是第三方依赖或历史遗留
- 该技术实际参与核心业务
- 该技术仅用于构建、开发或部署
- 该技术是否仍在使用尚不明确

**不要把“某项依赖出现在配置文件中”等同于“核心业务正在使用该技术”。**

### 原则二：以后端业务逻辑为主要分析重点

我对前端的关注程度低于后端。

请将分析精力主要放在：

1. 核心业务规则和业务流程
2. 后端服务、模块和架构
3. 跨服务、跨语言及模块间调用
4. 任务执行、工作流及状态流转
5. 数据结构、数据库和持久化
6. 异常处理、重试、权限及可靠性
7. 代码阅读与后续开发定位

对于前端，重点分析：

- 有哪些业务页面和功能入口
- 哪些页面对应哪些业务功能
- 前端向后端发送了什么请求
- 主要请求和响应的数据结构
- 如何从用户操作定位到后端接口

不需要逐个深入解释 CSS、样式、UI 组件和一般性的前端框架实现。

但是，如果实际发现重要业务逻辑存在于前端，仍需要分析，不要机械跳过。

**以业务逻辑所在位置为依据决定分析深度，而不是简单按编程语言分配工作量。**

### 原则三：业务理解优先于技术细节

分析顺序必须遵循：

业务目标 → 用户场景 → 功能模块 → 业务流程 → 系统架构 → 核心源码 → 技术细节

不要一上来就大量介绍类、函数、框架和配置。

每次分析重要技术模块时，优先回答：

- 它在业务中负责什么？
- 为什么系统需要它？
- 它接收什么数据？
- 它执行什么逻辑？
- 它向哪里输出结果？
- 它与哪些模块协作？

然后再解释具体实现。

### 原则四：基于真实源码，不能猜测充当事实

所有重要结论必须尽量附带可验证依据：

- 仓库相对文件路径
- 类名、函数名或方法名
- API 路由
- 配置项
- 相关代码位置
- 实际调用关系

引用代码时，优先使用 `文件路径 + 符号名称`，能够验证行号时再提供行号。

所有重要发现区分为：

- 【已确认】：源码、配置、测试或可信文档有明确依据
- 【合理推断】：根据相关证据推断，但未完全验证
- 【待确认】：缺乏足够证据，需要进一步调查

如果项目文档与实际代码不一致，以当前代码的可验证实现为优先依据，同时指出差异。

如果不能确认某项功能是否真正可用，不要仅凭接口或类名宣称功能已完整实现。

### 原则五：大型代码库采用渐进式分析

项目规模约 170 MB，不要一次性读取全部源码。

优先采用：

1. 项目目录与文件类型统计
2. 构建配置、依赖清单和入口文件检查
3. 现有技术文档及业务文档阅读
4. 关键类、接口、函数和符号检索
5. 通过调用关系逐步展开相关源码
6. 根据发现的证据按需深入

识别并跳过与业务分析无关的：

- `.git`
- `node_modules`
- `.venv`、`venv`
- `target`
- `build`
- `dist`
- 各类缓存目录
- 编译产物
- 自动生成的大型文件
- 二进制资源
- 无关的第三方依赖源码

不要因为文件数量多，就忽视业务关键但代码量较少的模块。

利用 Cursor 提供的代码检索和符号定位能力，尽量避免无目的地读取大量文件。

### 原则六：可以使用 Subagent，但由主 Agent 负责统一理解

允许根据实际仓库情况，使用 Explore Subagent 进行独立的只读检索任务。

例如：

- 独立后端服务调查
- 业务文档调查
- 数据库和基础设施调查
- 独立模块技术栈调查

主 Agent 必须承担：

- 全局业务理解
- 分析任务组织
- 核心模块优先级判断
- 跨模块调用链验证
- 不同调查结论交叉验证
- 最终文档整合

不要为了并行而强行拆分有依赖关系的工作。

不要求子 Agent 修改代码，也不要启动云端 Agent 或额外外部执行环境。

## 四、操作边界与安全要求

本次是代码理解和文档整理任务。

严格遵守以下限制：

1. 不修改、删除或重构任何现有业务代码。
2. 不安装依赖，不修改项目环境。
3. 不主动启动服务、数据库或后台任务。
4. 不执行部署、数据迁移或可能产生副作用的脚本。
5. 不调用真实业务接口来执行写入操作。
6. 不连接生产系统，不触发真实外部业务请求。
7. 不主动访问或输出密码、Token、私钥、真实客户敏感信息。
8. 对 `.env`、密钥文件及凭据材料，只识别其配置用途；优先查看脱敏示例文件，避免读取真实密钥。
9. 不额外上传源码、数据或文档到未经授权的外部服务。
10. 允许安全的本地只读目录查询、文本搜索、代码阅读和 Git 状态检查。

只有在后续阶段获得我的授权后，才允许在指定目录中创建新的 Markdown 分析文档。

除明确授权的文档外，不修改现有项目文件。

如果发现可能影响项目正常运行的操作，先报告，不要执行。

请先进行一轮轻量级、真实的仓库侦察。

### 0.3 制定项目专属分析计划

根据实际仓库特点，制定后续七个阶段的具体执行计划。

- 目标
- 优先调查的真实目录或文件
- 主要需要解决的问题
- 计划验证的技术与业务关系
- 预期产出
- 与其他阶段的依赖关系

根据实际发现调整工作量与优先级。

如果发现仓库不是典型的前后端架构，应重新组织分析范围，而不是机械执行预设结构。

### 0.4 阶段 0 输出要求

3. 项目目录结构简图
4. 初步判断的核心业务位置
5. 主要未知问题
6. 定制后的七阶段执行计划

**阶段 0 完成后必须停止，等待我确认执行计划。**

## 阶段 2：业务背景与功能模块梳理

这一阶段应优先建立业务理解，而不是深入研究框架细节。

### 2.1 理解项目业务

结合项目文档、接口定义、页面、数据模型及代码，分析：

1. 项目主要解决什么业务问题？
2. 主要使用者有哪些？
3. 各类用户使用系统的目的是什么？
4. 系统最重要的业务能力是什么？
5. 业务的输入与最终产出分别是什么？
6. 系统与外部业务平台之间存在什么关系？
7. 哪些流程是主要价值链路？

尽量使用通俗语言解释。

对于无法确认的业务背景，明确标记推断。

### 2.2 完整功能模块清单

将业务功能按业务领域分类，而不是简单按技术模块分类。

每个功能包含：

| 字段 | 内容 |
|---|---|
| 功能名称 | 该功能是什么 |
| 业务目的 | 解决什么问题 |
| 使用角色 | 谁会操作 |
| 用户入口 | 页面、API、任务等 |
| 输入 | 需要什么数据 |
| 处理 | 核心业务步骤 |
| 输出 | 最终产出 |
| 后端核心模块 | 实际实现位置 |
| 相关依赖 | 其他服务或组件 |
| 实现状态 | 已确认实现或待验证 |

### 2.3 还原用户操作流程

选取重要功能，分析：

- 用户执行了什么操作
- 系统收到什么请求
- 后端执行哪些业务处理
- 是否触发其他服务或任务
- 结果如何返回或保存
- 用户最终看到什么

如果某个功能没有前端，而是通过 API、消息、定时任务或其他系统触发，应按照真实入口描述。

### 2.4 提炼业务领域模型

识别核心业务实体、关键业务术语、状态及生命周期。

帮助我建立业务术语与实际代码之间的联系。

**阶段产出：项目业务说明、业务术语表、主要功能清单及业务流程地图。**

## 阶段 3：后端架构、核心逻辑与数据体系

**这是本次分析的最高优先级阶段之一。**

所有实际承担业务逻辑的后端语言、框架和服务都需要纳入分析。

不要局限于 Java 和 Python。

### 3.1 分析各个后端服务

对于每个重要服务，分别分析：

- 服务职责
- 使用的语言及框架
- 应用启动方式
- 代码分层和目录组织
- 核心接口
- 业务服务
- 主要数据模型
- 与其他服务的依赖
- 错误处理和日志
- 配置及环境依赖

根据项目真实架构选择分析对象。

不要强行套用 Controller、Service、Repository 等固定分层。

### 3.2 深入理解核心业务逻辑

重点调查：

- 核心业务规则
- 业务校验
- 重要数据处理算法
- 状态机和状态转换
- 工作流执行机制
- 同步与异步处理
- 后台任务执行
- 定时任务及调度
- 失败重试和异常恢复
- 事务与一致性处理
- 业务权限和访问控制

对于每个重要业务模块：

先解释业务目的，再解释核心实现，最后给出源码入口。

### 3.3 跨模块及跨服务通信

深入调查所有实际存在的交互方式，包括但不限于：

- HTTP / REST
- RPC / gRPC
- 消息队列
- 事件驱动
- 共享数据库
- 缓存
- 文件传递
- 任务队列
- 第三方 SDK 或 API

重点说明：

- 谁是调用方
- 谁是被调用方
- 如何定位调用入口
- 请求与响应格式
- 数据如何转换
- 是否同步或异步
- 失败如何处理

特别关注不同编程语言实现的服务之间如何协作。
